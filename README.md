# 토스증권 Open API 실측 기록

두 번째 파이프라인을 짓기 전에 재료부터 재 본 기록입니다. 2026년 9월 24일부터 10월 1일까지 8일 동안, 토스증권 Open API 가 어디까지 되는지 일곱 번 측정했습니다.

파이프라인은 아직 없습니다. 여기 있는 건 측정 스크립트 11개와 문서 4편입니다.

API 로 받은 데이터는 약관상 남에게 줄 수 없어서 저장소에 데이터, 시세 값, 캡처는 없습니다. 문서에 적힌 숫자는 전부 "API 가 어떻게 동작했나" 입니다. 유실률, 지연, 429 빈도, 순회 시간, 봉 개수 같은 것들입니다.

## 왜 이 API 였나

첫 프로젝트([crypto-cdc-pipeline](https://github.com/Aguantar/crypto-cdc-pipeline))는 코인 시세였고, 처리량과 실시간 검증이 중심이었습니다. 두 번째는 다른 종류의 어려움이어야 했습니다.

GH Archive 는 유명한 튜토리얼 데이터셋이라 설계 판단이 남지 않습니다. 서울 버스 위치는 맞았는지 확인할 기준이 없습니다. 제 앱의 이벤트 로그는 사용자가 적어 데이터가 적습니다.

토스증권 API 는 쿼터가 진짜입니다. 웹소켓 연결은 계정당 2개, 연결당 구독 100개, REST 는 그룹별 초당 한도가 있습니다. 그래서 "국내 4천 종목을 어떻게 덮을 것인가" 가 설계 문제가 됩니다. 실시간 체결 스트림과 별도로 1분봉이 있어서 스트림이 맞았는지 확인할 기준도 있습니다. 키는 이미 승인받아 둔 상태였습니다.

다만 문서를 읽기 전에는 이 API 로 뭘 할 수 있는지 몰랐습니다. 그래서 설계보다 측정을 먼저 했습니다. 측정 전에 세워 둔 계획의 숫자 중 셋이 측정 뒤에 틀린 것으로 드러났습니다.

## 8일 동안 한 일

**9월 24일 목, 낮.** 공개 문서 6종을 읽었습니다. OpenAPI 3.1 과 AsyncAPI 3.0 정본, FAQ, 개요. REST 33개 경로, 웹소켓 채널 3개, 한도 표, 약관을 노트로 정리했습니다. 약관의 "본인의 매매 목적에 한하여" 를 처음엔 이용 금지로 넓게 읽어서 "이 API 는 못 쓴다" 고 했다가, 다시 읽고 정정했습니다. 규제 대상은 제3자 배포와 상업 이용입니다. (docs/00)

이날이 추석이라 국내 장이 닫혀 있었습니다. 처음엔 정규장 중이라고 생각했는데 지적을 받고 알았습니다. 덕분에 REST 만 깨끗하게 쟀습니다. 토큰, 달력, 한도, 1분봉 구조. 달력 API 가 휴장일에 세션을 null 로 돌려줘서 "안 오는 게 정상" 을 판정할 근거가 API 안에 있다는 걸 확인했습니다. 한도는 캔들 60요청을 동시에 던져 200 응답 21개, 429 응답 39개를 받아 문서의 "토큰 버킷 20" 이 그대로임을 확인했습니다. 1분봉은 하루 720개, 빈틈 0, 중복 0 이었습니다. (docs/01 §1~4)

미국 데이마켓은 열려 있어서 웹소켓을 10종목 6분 받아 봤습니다. 미국 종목을 `trade:kr` 로 선언해서 10개 전부 거부당했습니다. 허용 IP 문제인 줄 알았는데 handshake 와 ack 가 정상이라 IP 는 아니었고, 심볼로 시장을 판별하게 고쳤습니다. 받은 체결을 분 단위로 합쳐 1분봉 거래량과 셀마다 비교했더니 34셀 전부 일치했습니다. 부하가 없는 곳에서 대조 방법이 맞다는 것부터 확인한 셈입니다. (docs/01 §5)

**9월 24일 목, 밤 22:31.** 미국 정규장이 열리는 시각에 cron 으로 연결당 한도인 100종목을 10분 받았습니다. 212,508 프레임, 초당 최대 798건, 878셀 전부 일치, 재연결 0. 한도를 꽉 채운 개장 직후에도 한 건도 안 빠졌습니다. (docs/01 §7)

**9월 26일 토.** 장이 닫혀 값이 안 움직이니 순회 측정에 좋은 날입니다. 전 종목 목록을 받으니 국내가 4,304종목이었습니다. 계획에 2,600 이라 적어 둔 건 추정이었고 틀렸습니다. 하루치 1분봉을 전 종목 돌리는 데 12분, 요청 13,691개, 429 가 105번 났습니다. 초당 20 아래로 보내도 버킷 경계에서 0.8% 는 걸립니다. 수정주가 적용본과 미적용본을 60일치 받아 비교하니 604종목이 달랐습니다. 459개는 월배당 ETF 의 분배락이라 7월 29일, 8월 27일, 9월 11일에 몰려 있었습니다. (docs/03)

**9월 28일 월, 10:40.** 국내 첫 거래일. 장중 평시에 100종목 10분. 857셀 전부 일치. 지연이 p50 13ms 였습니다. 미국은 640ms 였는데, 그건 거래소에서 토스까지의 고정 지연이었고 국내엔 없습니다. 개장 직후를 재려 했지만 cron 을 안 걸어 놓쳐서 다음날로 예약했습니다. (docs/01 §8)

**9월 29일 화, 08:59.** 국내 개장 직후 100종목 10분. 시가 단일가 체결이 몰리는 가장 거친 구간입니다. 184,478 프레임, 초당 최대 1,058건, 719셀 전부 일치. 지연은 최대 3.2초까지 늘었지만 빠진 건 없었습니다. (docs/01 §9)

**10월 1일 목, 08:04~20:05.** 남은 미측정은 둘이었습니다. 연결 2개를 동시에 쓰면 어떤지, 하루 종일 켜 두면 재연결이 몇 번 나는지. 연결 2개에 100종목씩 200종목을 12시간 받고 20:12 에 cron 으로 1분봉 하루치와 대조했습니다. 312만 메시지, 재연결 0, 오류 프레임 0. 78,942셀 중 78,543셀이 정확히 일치했고 거래량 합은 99.956% 였습니다. 종목을 거래대금 순으로 앞뒤 100개씩 나눴더니 한 연결이 다른 연결의 10배를 받았습니다. 부하는 연결이 아니라 종목에 몰리니 섞어서 배정해야 합니다. (docs/01 §10)

불일치 399셀을 다음날 다시 조회해 분류했습니다. 정규장 연속 체결 구간은 4셀뿐이고 나머지는 종가 단일가 창과 시간외 구간이었습니다. 여기서 두 가지가 나왔습니다. 종가 단일가 체결이 든 봉이 종목마다 달랐습니다. 85종목은 15:30 봉, 83종목은 15:31 봉. FAQ 는 15:31 봉이라고 했는데 절반에만 맞았습니다. 그리고 종가 창을 두 봉의 합으로 보면 199종목 중 48종목에서 웹소켓이 1분봉보다 적었습니다. 중앙값 91%. 원문 프레임을 저장하지 않아 원인은 못 갈랐습니다.

## 알게 된 것

1분봉의 timestamp 는 봉 종료 시각입니다. 09:01 봉이 09:00:00 부터 09:00:59 까지입니다. 대조할 때 체결 분에 1을 더해야 맞고, 이 하나가 틀리면 전 셀이 어긋납니다.

유실은 서버가 아니라 클라이언트에서 납니다. 한도를 꽉 채운 개장 직후에도 안 빠졌습니다. 채널이 LOSSY 라는 건 수신이 밀리면 빠질 수 있다는 면책이지 상시 손실이 아닙니다. 첫 프로젝트에서 수집기가 못 따라가 빠진 것과 같은 유형이고, 그 임계는 이 규모에선 못 쟀습니다.

"빠짐없이 받았다" 는 종목별 기준입니다. 하루 720봉은 종목의 4분의 1에만 해당합니다. 프리마켓이 없는 종목은 660, KRX 정규장만 있는 종목은 390입니다. 유형만으로는 안 갈려서 첫 순회 때 종목별로 재 두어야 합니다.

기업행위는 매달 수백 건입니다. 정정 이력은 있으면 좋은 게 아니라 매일 생기는 일입니다.

한도는 토큰 버킷입니다. 순차로 보내면 한도에 못 닿고, 병렬로 보내면 첫 1초에 버킷만큼만 받습니다. Retry-After 가 정수 초라 재시도 최소 단위는 1초입니다.

국내 웹소켓은 시간외 체결도 보냅니다. 하루 셀의 30% 가 15:30 이후였습니다.

## 못 푼 것

종가 단일가 창에서 48종목이 웹소켓 쪽이 적었던 이유. 웹소켓이 종가 체결 일부를 안 보내는 건지, 1분봉이 그 봉에 다른 체결을 합치는 건지 모릅니다. 다음 세션은 15:25 부터 15:35 까지만 원문을 남겨서 가를 생각입니다.

클라이언트가 못 따라가기 시작하는 초당 건수. 같은 분 안의 체결 순서. 체결 건수 대조는 1분봉에 건수가 없어 못 합니다. 그리고 200종목은 전체의 4.6% 입니다.

## 측정이 바꾼 것

처음 계획은 "LOSSY 스트림의 유실을 매일 증명하는 파이프라인" 이었습니다. 측정하니 이 규모에선 유실이 안 보였습니다. 그래서 중심이 커버리지와 정정 이력으로 옮겨갔습니다.

폴링 계층을 2~3분 지연이라 적었는데 한 바퀴가 12분입니다. 장중엔 최신 봉만 받아 3.6분으로 줄입니다.

저장은 Oracle 인스턴스에 Iceberg 까지 두려 했는데, 인스턴스가 2코어에 여유 6GB 라 오브젝트 스토리지와 Parquet, DuckDB 로 시작합니다.

첫 결정은 유니버스에 ETF 와 ETN 을 넣을지입니다. 넣으면 정정 이력의 대부분이 분배락이 됩니다.

첫 프로젝트에서 가져온 건 방법입니다. 스트림을 분 단위로 합쳐 기준값과 셀마다 대조하는 것, cron 실행 이력으로만 완료를 말하는 것, 숫자는 조건과 같이 적는 것. 스택은 안 가져옵니다. 이 규모엔 Kafka 도 Flink 도 ClickHouse 도 필요 없다는 게 측정의 결론입니다.

## 저장소

```
scripts/
  common.py             토큰 발급, GET, 한도 헤더. 표준 라이브러리만
  token_check.py        접속 확인
  rest_candles.py       종목별 1분봉 조회
  ws_record.py          웹소켓 체결 녹화
  reconcile.py          녹화 vs 1분봉 셀 대조
  top_symbols.py        랭킹으로 종목 선정
  burst_test.sh         녹화, 조회, 대조를 cron 한 번에
  universe.py           전 종목 목록
  sweep_1m.py           전 종목 순회, 수정주가 두 벌 비교
  ws_session.py         하루 세션 녹화 (연결 2 × 100, 분 단위 집계만)
  session_reconcile.py  세션 셀 vs 1분봉 하루치 대조
docs/
  00-api-notes.md            문서 조사 노트와 약관 해석
  01-first-measurements.md   측정 7회의 조건과 결과
  02-plan-draft.md           측정 전 초안과 측정 뒤 결론
  03-universe-and-sweep.md   유니버스, 달력, 전 종목 순회
  worklog.md                 시각별 작업 기록
```

`.env` 에 클라이언트 키 둘이 필요합니다. 웹소켓 스크립트는 websockets 패키지가 있는 컨테이너에서 돌렸고 나머지는 표준 라이브러리만 씁니다. `data/`, `*.jsonl`, `*.log`, 토큰은 .gitignore 에 있고 어느 커밋에도 들어간 적이 없습니다.
