# 02. 두 번째 파이프라인 계획 (초안, 2026-09-24 06:00 UTC)

> 초안이다. 아래 "실측 뒤 정할 것" 이 채워지기 전에는 확정하지 않는다. 확정 근거는 docs/01 과 이후 측정 문서.

## 0. 한 문장

토스증권 Open API 의 **쿼터(연결 2 · 구독 100 · 그룹별 초당 한도)** 안에서 국내 상장 종목 전체를 "빠짐없이" 덮고,
시퀀스 없는 LOSSY 스트림의 유실을 **캔들 대조로 매일 증명**하며, 기업행위로 바뀌는 과거 값을 **정정 이력**으로 남기는 파이프라인.
첫 프로젝트(코인, 처리량과 실시간 검증)와 겹치지 않는 것만 한다: 쿼터 안 커버리지, 배치 정합성, 정정 이력, 달력, 클라우드 저장.

## 1. 왜 이 프로젝트인가 (판단 기록)

- 첫 프로젝트의 약점은 아키텍처 규모(브로커 1, Flink 과함)이고, 강점은 검증 기록이다. 두 번째는 규모 자랑이 아니라 **다른 종류의 어려움**이어야 한다.
- 후보 비교: GH Archive(유명 튜토리얼 데이터셋, 진실값은 좋음) · 서울 버스(진실값 없음) · 자기 제품 이벤트(사용자 적음) · **토스증권 API**(제약이 진짜, 진실값(캔들) 있음, 지원 대상 회사, 반나절에 첫 측정).
- 약관: 제3자 배포·상업 금지. 본인 사용과 코드·구조 공개는 문제 없음(docs/00 §6). 처음에 이용 금지로 넓게 읽어 "안 된다" 고 했다가 정정한 기록을 남긴다.

## 2. 확인된 사실 (docs/00·01)

| 항목 | 값 |
|---|---|
| 실시간 | 웹소켓 연결 2/계정, 구독 100/연결, 선언 5회/초. 시세 채널 LOSSY, 시퀀스·체결ID 없음, data = price·volume·timestamp·currency |
| REST | 캔들 200개/요청, 초당 20 (버킷 20 실측). 시세 초당 15. 종목 초당 5, 전체 목록 초당 1. 체결 최근 50건, 과거 페이지네이션 없음 |
| 봉 규칙 | `1m` timestamp = 봉 종료 시각. 체결 분 + 1 = 봉. 국내 08:01~20:00 720봉/일, 09-23 실측 빈틈·중복 0 |
| 달력 | KR `integrated: null` 이면 휴장. US 는 데이마켓·프리·정규·애프터 세션 시각 제공 |
| 지연 | 미국 데이마켓(얇음) 수신 지연 p50 0.74s, p95 1.16s. 대조 34셀 100% |
| 과거 | 국내 2022-11-23 이후. 캔들 사후 정정 없음, 기업행위는 `adjusted` 수정비율로만 |

## 3. 실측 뒤 정할 것 (이 결과가 설계를 바꾼다)

| 측정 | 언제 | 결정에 미치는 영향 |
|---|---|---|
| 미국 정규장 개장 직후, 구독 100, 10분 | **09-24 13:31 UTC 완료 (docs/01 §7)** | 초당 max 798 에서 878셀 100% 일치, 재연결 0, 지연 p50 0.64s 평탄. 유실은 서버가 아니라 클라이언트 역압 문제로 본다 → 실시간 계층은 200 종목까지 그대로, 소비자에 lag·큐 길이 지표를 처음부터 넣는다 |
| 국내 개장 직후(09:00~09:10), 구독 100 | **09-29 완료 (docs/01 §9)** | 719셀 100%, 초당 max 1,058, 지연 p50 10ms·max 3.2s. 유실 0. 실시간 계층 200 유지 |

| `adjusted` true/false 두 벌 비교 | **09-26 완료 (docs/03 §4)** | 60일 창에 **604 종목**(ETF 459 분배락 · 주식 142 배당락·분할). 정정 이력은 매달 수백 건. 일봉 두 벌 전 종목 7.5분 |
| 체결 REST 50건이 실제로 몇 초를 덮나 | 09-28 | 복구 수단이 되는지(아마 아님) 확정 |
| Oracle 인스턴스 사양·남은 한도 | **10-01 확인** | ARM 2코어(Neoverse-N1), RAM 11GB 중 사용 4GB(ES 3.0·hotel 0.9·kibana 0.7)·여유 6GB, 디스크 45GB 중 24GB 사용, 컨테이너 9개. DuckDB+Parquet 은 가능, ES 와 같이 쓰면 여유 3GB 안팎. Iceberg 카탈로그(JVM)는 부담 - 오브젝트 스토리지 + Parquet + DuckDB 로 시작하고 Iceberg 는 필요해질 때 |

## 4. 아키텍처 (초안)

원칙: 규모에 맞게. 스트림 엔진 없음, 저장소와 스케줄러가 대부분을 한다. 첫 프로젝트에서 배운 것의 적용.

| 층 | 초안 | 근거 / 대안 |
|---|---|---|
| 실시간 계층 (레인 A) | Python 웹소켓 소비자 1~2 프로세스, 상위 100~200 종목(거래대금 랭킹으로 매일 갱신) → 로컬 큐/파일 → 저장소 | 쿼터가 상한. 큐는 Kafka 가 아니라 파일 append 또는 Redis Streams 정도. 초당 수천 건 이하 예상(실측 뒤) |
| 폴링 계층 (레인 B) | 전 종목 1분봉을 초당 20 안에서 순회(병렬 N, 429 시 Retry-After 준수). 장중 2~3분 지연, 장 마감 후 당일 전체 재수집 | 진실값이자 백필. `before` 페이지네이션으로 과거 구간 재처리 가능 |
| 대조 (레인 C) | 레인 A 의 (종목, 분) 거래량 합 vs 레인 B 봉 volume. 셀 단위 일치율·불일치 셀 목록·최악 셀 | 첫 프로젝트의 셀 대조 그대로. 이번엔 "실시간이 얼마나 빠지나" 를 매일 잰다 |
| 정정 이력 (레인 D) | 일봉 `adjusted=true/false` 두 벌을 매일 저장, 수정비율 변화 = 기업행위 감지 → 스냅샷 버전 | 시점 조회가 요구사항. Iceberg 스냅샷 또는 버전 컬럼 |
| 달력·상태 | `market-calendar` 로 세션 판정, `stocks/{symbol}/warnings` 로 정지·경고 라벨 | "안 오는 게 정상" 의 근거 |
| 저장 | **1안** Oracle 인스턴스의 DuckDB + Parquet(오브젝트 스토리지) + Iceberg 카탈로그. **2안** Oracle 이 작으면 미니PC ClickHouse 에 표 추가(겹침 큼, 비추천) | 클라우드·파일 레이크 공백을 채우는 것이 목적. 규모(하루 수십만~수백만 행)는 DuckDB 로 충분 |
| 변환 | dbt (duckdb 어댑터) | 레인 C·D 의 표를 dbt 테스트·계약과 함께 |
| 오케스트레이션 | Dagster (시간·거래일 파티션) 또는 Airflow 재사용 | 거래일 달력 파티션이 핵심. Dagster 로 하면 첫 프로젝트와 비교 서술 가능 |
| 인프라 | Terraform (OCI 인스턴스·버킷·IAM), compose | 첫 프로젝트에 없던 IaC |
| 관측 | 레인별 지연·429 횟수·재연결·셀 불일치 수를 일별 표로, 알림은 Slack 1채널, 시간당 1회 억제(docs/44 교훈) | Grafana 는 공개 안 함(약관) |
| 인증·비밀 | 클라이언트 키는 .env, 토큰 캐시 600. 허용 IP 는 Oracle 공인 IP 등록 필요(바뀌면 403) | FAQ 의 "클라우드 IP 변동" 경고 |

안 넣는 것: Kafka·Flink·ClickHouse(2안 제외)·공개 대시보드·실돈 주문(별도 결정 전까지).

## 5. 검증 기준 (각 단계의 "됐다" 의 정의)

| 단계 | 산출 | 검증 |
|---|---|---|
| 1. 레인 B 전 종목 순회 | 국내 2,600 종목 1분봉 하루치 | 봉 수 = 720 × 거래 종목 수, 빈틈 0, 429 횟수·순회 시간 기록 |
| 2. 레인 A 상위 N | 장중 체결 수집 | 재연결 횟수, 지연 p95, 일별 셀 일치율(레인 C) |
| 3. 레인 C | 일별 대조 표 | 불일치 셀이 0 이 아니면 원인 분류(유실·봉 경계·단일가·정지) |
| 4. 레인 D | 정정 이력 | 첫 기업행위에서 과거 값 변화가 스냅샷으로 잡힘 |
| 5. 달력 | 휴장·세션 판정 | 09-24~26 같은 휴장에 레인 A 가 안 켜지고 알림도 없음 |
| 6. 클라우드 | Terraform 으로 재현 | 새 인스턴스에 처음부터 올려 1~5 가 다시 도는지 |

## 7. 위험

- 부하에서 유실이 커서 실시간 계층이 "속보" 이상이 못 될 수 있다 → 그래도 프로젝트는 성립(그 사실을 재는 것이 목적)
- Oracle 공인 IP 변동 → 허용 IP 갱신 절차 필요, 403 을 알림으로
- 약관 해석은 내 것. 이용약관 전문 확인 전까지 데이터·캡처는 어디에도 안 올린다
- 첫 프로젝트와 겹쳐 보일 위험 → 무게를 처리량이 아니라 쿼터·정합성·정정에 둔다는 것을 README 첫 절에서 못 박는다

## 8. 공개 범위 (docs/00 §8 재확인)

코드·문서·Terraform 공개. `data/`·`.env`·토큰·시세 캡처 비공개. 문서 숫자는 API 동작 측정(유실률·지연·429·순회 시간)까지, 특정 종목의 가격은 적지 않는다.


## 9. 실측 뒤 결론 (10-01)

측정 6개 중 5개가 끝났다(연결 2개 동시·장시간 재연결 빈도만 남음). 결론:

1. **실시간 채널은 이 구독 규모에서 믿어도 된다.** 미국 개장·국내 장중·국내 개장 세 번 모두 셀 100%. 국내 지연은 수십 ms. "유실 측정" 은 서사가 아니다.
2. **문제는 커버리지다.** 유니버스 4,304(주식 2,715 + ETF·ETN 1,540). 실시간 200 + 폴링 순회 12분. 종목마다 세션 프로파일(720/660/390)이 달라 "빠짐없음" 은 종목별 기준으로 판정해야 한다.
3. **정정 이력은 매달 수백 건이다.** 60일에 604 종목(ETF 분배락 459, 주식 142). 두 벌(adjusted true/false)을 매일 받아 스냅샷으로 남기는 것이 이 프로젝트의 중심.
4. **저장은 Oracle 오브젝트 스토리지 + Parquet + DuckDB.** 인스턴스는 2코어·여유 6GB 라 처리 층을 둘 수는 있으나 ES 와 나눠 써야 한다. Iceberg 는 필요해질 때.
5. 첫 결정은 유니버스 정의(ETF·ETN 포함 여부). 포함하면 정정 이력의 대부분이 분배락이 된다.
6. 우선순위는 지원서 > 이 프로젝트. 착수하면 docs/02 §6 의 1주차(레인 B: 전 종목 캔들이 빈틈 없이 쌓이는 것)부터.
