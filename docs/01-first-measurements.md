# 01. 첫 실측 (2026-09-24 05:30~ UTC, 국내 휴장일)

국내는 추석 휴장(09-24~26, 다음 거래일 09-28). 그래서 오늘은 한도·달력·캔들 구조를 재고, 실시간 레인은 미국 데이마켓으로 잰다.
시세 값은 이 문서에 적지 않는다(약관, docs/00 §8). 적는 것은 API 의 동작에 대한 측정뿐이다.

## 1. 접속

`POST /oauth2/token` 정상, 토큰 길이 834. 토큰만으로 캘린더·종목·캔들 조회 OK. 응답 헤더에 `X-RateLimit-Limit/Remaining/Reset` 이 문서대로 온다.

## 2. 달력이 휴장을 안다

| | 응답 |
|---|---|
| KR `today` | `{"date":"2026-09-24","integrated":null}` - 세션 정보가 null. 이전 거래일 09-23, 다음 09-28 |
| US `today` | dayMarket 09:00~17:00 KST, preMarket 17:00~22:30, regularMarket 22:30~05:00, afterMarket 05:00~08:50 (다음날) |

"안 오는 게 정상" 을 판정할 근거가 API 에 있다. 파이프라인은 KR `integrated=null` 인 날 실시간 레인을 안 켜야 한다.

## 3. Rate Limits 실측

| 실험 | 결과 |
|---|---|
| 순차 요청(미니PC 왕복 약 140ms) 캔들 40회·시세 30회 | 전부 200. 순차로는 초당 7회라 20·15 한도에 못 닿는다 |
| 순차 종목 조회 12회 (한도 5) | 7번째(0.92초)부터 429, `Retry-After: 1`, 200=10 429=2 |
| **동시** 캔들 60회 (한도 20) | 1.44초 안에 200=**21** 429=39. 첫 429 는 35번째 응답(1.24초). `Remaining` 0, `Reset` 1, `Retry-After` 1 |

해석: 문서의 "토큰 버킷, Limit=burst capacity" 그대로다. 버킷 20 이 한 번에 비고 초당 20 으로 찬다. 순차 클라이언트는 한도를 못 넘기고,
병렬 클라이언트는 첫 1초에 버킷만큼만 받는다. 전 종목 캔들 순회 설계는 "초당 20회 × 200봉" 이 상한이다.
`Retry-After` 가 정수 초라 재시도는 1초 뒤가 최소 단위. 원 데이터: `data/ratelimit_*.jsonl`, `data/ratelimit_burst_*.json`.

## 4. 국내 1분봉 구조 (09-23, 삼성전자, `before` 페이지네이션 5회)

| 항목 | 결과 |
|---|---|
| 페이지 | 200개씩, `nextBefore` 가 다음 페이지의 첫 봉 시각(inclusive). 4페이지에서 전날로 넘어감 |
| 09-23 봉 수 | **720** = 08:01~20:00 정확히 12시간, 1분 간격 빈틈 0, 중복 0 |
| 경계 봉 | 08:01(첫), 09:00, 09:01, 15:30, 15:31, 20:00(끝) 전부 존재. FAQ 의 "timestamp 는 봉 종료 시각" 과 맞는다 - 08:01 봉이 08:00:00~08:00:59 |
| 거래량 0 봉 | 29 (체결 없는 분, OHLC 는 직전 종가 - FAQ) |

대조 규칙이 정해진다: 체결 timestamp 의 분을 버리고 +1분 한 것이 그 체결이 속한 봉이다. 단일가 구간(15:20~15:30 접수)은 15:31 봉에 몰린다.

## 5. 미국 데이마켓 웹소켓 (05:41~05:47 UTC, 10 종목, 6분)

먼저 내 실수 하나: 미국 종목을 `trade:kr` 로 선언해 10개 전부 `symbol-market-mismatch` 로 거부됐다(허용 IP 문제로 의심했으나 handshake·ack 는 정상, 즉 IP 는 등록돼 있다).
심볼로 시장을 판별하게 고친 뒤:

| 항목 | 결과 |
|---|---|
| 구독 ack | 10/10 `subscribed`, 거부 0 |
| 프레임 | 6분 1,231 (message 1,226 + pong 5), 재연결 0. 종목별 편차 큼(SOXL 602, AAPL 28) - 데이마켓이라 전체 초당 약 3.4건 |
| data 키 | `currency, price, timestamp, volume` 뿐. 체결 ID·시퀀스·누적거래량 없음(문서대로) |
| 수신 지연 (recv_ts − 체결 timestamp) | p50 **0.74초**, p95 **1.16초**, min 0.18, max 1.20 |
| **대조** (완결된 분만, 봉 = 체결 분 + 1) | **34셀 전부 일치, 거래량 합 26,760 = 26,760 (100.000%)** |

해석: 부하가 거의 없는 구간에서는 LOSSY 채널도 한 건도 안 빠지고, 봉 경계 규칙(체결 분 + 1 = 봉 timestamp)이 미국 시세에도 그대로 맞는다.
이건 "유실 없음" 의 증명이 아니라 **대조 방법이 맞다는 증명**이다. 진짜 측정은 부하가 있을 때다: 미국 정규장(22:30 KST~)에서
같은 10 종목 + 구독을 100까지 늘린 상태, 그리고 09-28 국내 개장 직후(09:00~09:10). 그때 셀 불일치가 나오면 그게 이 채널의 유실률이다.

원 데이터: `data/ws_trades_20260924T054113Z.jsonl`, `data/candles_20260924T054718Z.jsonl` (저장소 밖).

## 6. 오늘 확인된 것 / 남은 것

확인: 인증·한도(버킷 20 실측)·달력(휴장 판정)·캔들 구조(720봉, 경계 규칙)·웹소켓(구독·keepalive·프레임 스키마·지연)·대조 방법(100% 일치).
남은 것: 부하 구간 유실률(미국 정규장, 국내 개장), 구독 100·연결 2 한도에서의 동작, `adjusted` 두 벌 비교(기업행위 정정 이력), 체결 REST 50건 한도의 실제 의미.

## 7. 미국 정규장 개장 직후, 구독 100 (13:31:02~13:41:02 UTC = 22:31 KST, cron 자동 실행)

조건: 당일 거래량 랭킹 상위 100 종목을 **연결 1개에 100 구독(연결당 한도)**, 10분. 미니PC 의 Python 소비자 1개(파일 append).

| 항목 | 결과 |
|---|---|
| 구독 | 100/100 ack, 거부 0 |
| 프레임 | **212,508** (message 212,499 + pong 9), 재연결 0 |
| 초당 메시지 | p50 **345**, p95 492, **max 798** (13:31:23) |
| 종목 편차 | 상위 5 종목이 12,213 · 11,929 · 9,679 · 8,487 · 7,395 (전체의 23%) |
| 수신 지연 (recv − 체결 timestamp) | p50 **0.636s**, p95 1.142s, p99 1.433s, max 2.94s. 분별 p50 0.61~0.67s 로 10분 내내 평탄 |
| **대조** (완결 878셀, 봉 = 체결 분 + 1) | **878/878 일치, 거래량 합 120,205,292 = 120,205,292 (100.000%)** |

해석:
- 연결당 한도(100 구독)를 꽉 채운 정규장 개장 직후 10분, 초당 최대 800 건에서 **한 건도 안 빠졌다.** LOSSY 는 "빠질 수 있다" 는 서버의 면책이지 상시 손실이 아니다.
  이 채널의 유실 위험은 서버가 아니라 **클라이언트가 못 따라갈 때**(첫 프로젝트 09-23 Binance 사건과 같은 유형)로 보는 게 맞다. 그 임계는 여기서 못 쟀다 - 최대 800/s 는 Python 소비자에 전혀 부담이 아니었다.
- 지연 0.6초는 부하와 무관하게 평탄하다 → 클라이언트 지연이 아니라 서버 쪽 고정 지연. 실시간 계층의 값은 "0.6~1.4초 뒤" 라고 말할 수 있다.
- 연결 2개 × 100 = 200 종목이면 초당 약 700(평균)~1,600(피크) 건 예상. 첫 프로젝트 수집기 한계(약 1만/s)의 1/6 이하.
- 남은 미측정: 국내 개장 09:00~09:10 (단일가 체결이 09:01 봉에 몰림, 국내 상위 100 의 초당 건수), 연결 2개 동시, 장시간(하루) 재연결 빈도.

원 데이터: `data/ws_trades_20260924T133102Z.jsonl`(212k 행), `data/candles_20260924T134102Z.jsonl`, 로그 `data/burst_20260924T133101Z.log`.

## 8. 국내 장중 (09-28 월 10:40:44 ~ 10:50:44 KST, 구독 100, 정규장 평시)

개장 폭주(09:00~09:10)는 이날 cron 을 걸지 않아 놓쳤고 09-29 08:59 KST 로 예약했다. 이건 장중 평시 값이다.

| 항목 | 결과 |
|---|---|
| 구독 | 100 선언, 데이터가 온 topic 99 (10분간 체결 없는 종목 1) |
| 프레임 | **151,952** / 10분, 재연결 0 |
| 초당 메시지 | p50 **231**, p95 419, max 728 |
| 수신 지연 (recv − 체결 timestamp) | p50 **0.013초**, p95 0.080, p99 0.291, max 1.89 |
| 대조 (완결 857셀, 봉 = 체결 분 + 1) | **857/857 일치, 거래량 합 230,625,384 = 230,625,384 (100.000%)** |

해석: 국내 체결 웹소켓은 미국(p50 0.64초)과 달리 **수십 ms** 지연이다. 미국 시세의 0.6초는 거래소 → 토스 경로의 고정 지연이었고 국내는 그것이 없다.
봉 경계 규칙(체결 분 + 1)은 국내 통합 시세에서도 그대로 맞는다. 평시 초당 231~728건은 첫 프로젝트 수집기 한계(약 1만/초)의 1/10 아래.

## 10. 하루 세션 녹화 (10-01 목 08:04 ~ 20:05 KST, 연결 2 × 구독 100 = 200 종목)

남은 미측정 둘(연결 2개 동시, 하루 재연결 빈도)을 한 번에 잰다. 원문은 저장하지 않고 분 단위(msgs, lag p50/p95/max, 연결별)와 (종목, 봉) 셀만 집계한다.
종목은 거래대금 상위 100 ∪ 거래량 상위 100, 부족분은 KOSPI 주식으로 채워 200. 끝나면 `scripts/session_reconcile.py` 가 20:12 KST 에 1분봉 하루치와 대조한다(cron 1회).
결과는 아래에 적는다.
